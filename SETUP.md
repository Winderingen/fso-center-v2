# Новый сайт: запуск только через браузер

Комплект подготовлен 17.10.2026. Он включает сегодняшние изменения и не привязан к прежнему репозиторию или прежнему Supabase. Во всех шагах используйте **новый** проект и **новый** репозиторий.

Для примеров ниже выбрано имя репозитория `fso-center-v2`. Его можно заменить своим. Если владелец GitHub — Winderingen, итоговый адрес будет `https://winderingen.github.io/fso-center-v2/`. Никакие новые ресурсы от вашего имени автоматически ещё не созданы.

## 1. Скачайте и распакуйте комплект

Распакуйте `fso-center-new-project.zip` в новую папку. Внутри должны быть site, supabase, scripts, tests, .github, package.json, README.md и SETUP.md. Загружать в GitHub далее нужно **содержимое** этой папки, не ZIP и не внешнюю папку-обёртку.

Старые обновления, архивы, database.sqlite, .runtime и старый config.js в новый репозиторий не переносите. Миграция старых результатов не входит в этот запуск; новая база создаётся чистой.

## 2. Создайте новый репозиторий GitHub

1. GitHub → «+» → New repository.
2. Repository name: например `fso-center-v2`.
3. Выберите Public для обычного размещения через GitHub Pages.
4. Включите Add a README file, чтобы сразу существовала ветка main.
5. Create repository.
6. Settings → Pages → Build and deployment → Source → **GitHub Actions**. Если этот выбор пока не доступен, вернитесь к нему после загрузки workflow в шаге 8.

Запишите будущий адрес сайта. Для другого аккаунта замените имя владельца. Используйте стандартный github.io-адрес без собственного домена на первом запуске.

## 3. Создайте новый проект Supabase

1. В Supabase Dashboard выберите New project и свою организацию.
2. Укажите имя, например `fso-center-v2`, пароль базы и регион. Сохраните пароль базы у себя: это **не** пароль администратора сайта.
3. Дождитесь готовности проекта.
4. Скопируйте **Project ref / Reference ID** нового проекта. Он виден в настройках и в адресе Dashboard: `/project/ВАШ_REF`. Это 20 символов; не URL целиком.
5. Откройте Connect или Project Settings → API Keys. Скопируйте **Publishable key** (`sb_publishable_...`). Если используете legacy-ключи, допускается anon key. Не выбирайте secret или service_role.

Не используйте ref или ключ прежнего Supabase. Публичный ключ и project ref должны принадлежать одному новому проекту.

## 4. Создайте схему и начальные данные

1. В **новом** Supabase откройте SQL Editor → New query.
2. Откройте `supabase/setup.sql` из распакованного архива обычным текстовым редактором.
3. Скопируйте весь файл в SQL Editor и нажмите Run.
4. Ожидается успешное выполнение. Если интерфейс предупреждает об изменении прав/создании функций, это ожидаемые операции схемы данного файла; убедитесь, что выбран именно новый проект.
5. Для проверки выполните отдельно:

```sql
select id, version,
       jsonb_array_length(data->'questions') as question_count,
       jsonb_array_length(data->'attempts') as attempt_count
from public.fso_state
where id = 1;
```

Ожидаются одна строка с id=1, 6 учебных вопросов и 0 попыток. Несколько учебных материалов — заглушки. Пробный экзамен пока не опубликован и не имеет кодового слова.

Не нужно отдельно выполнять файл migrations/202610050001_trial.sql: setup.sql уже содержит схему и начальное наполнение. Повторный запуск setup.sql не заменяет существующую запись, но не используйте его как способ сбросить или восстановить данные.

## 5. Создайте администратора сайта

1. Supabase → Authentication → Users → Add user → Create new user (название пункта может отличаться в языке Dashboard).
2. Укажите собственный действующий email и отдельный пароль администратора.
3. Если есть Auto Confirm User / Email confirmed, включите. Если пользователь создан приглашением, сначала завершите подтверждение email и установку пароля.
4. Откройте пользователя и скопируйте его **User UID / UUID**.
5. В Authentication → Sign In / Providers / настройках регистрации выключите **Allow new users to sign up**: посетителям сайта аккаунты не нужны. Вход по email/password оставьте включённым.

Запишите желаемое имя входа на сайт, например `academy_admin`. Это имя будет связано с email через настройку ниже. Локальные admin/FsoDemo2026! не являются облачной учётной записью.

## 6. Настройте пять секретов функции Supabase

Supabase → Edge Functions → Secrets → Add/Manage secrets. Если функция ещё не отображается в списке, ищите общую вкладку Secrets раздела Edge Functions; создавать временную функцию-шаблон не требуется.

| Имя | Значение |
|---|---|
| FSO_ADMIN_UID | UUID нового администратора из Authentication |
| FSO_ADMIN_EMAIL | Email этого же пользователя |
| FSO_ADMIN_LOGIN | Желаемый логин сайта, например academy_admin |
| FSO_CODE_PEPPER | Новый случайный длинный секрет, см. ниже |
| FSO_SITE_ORIGIN | Только origin GitHub Pages, например https://winderingen.github.io |

В FSO_SITE_ORIGIN **нет** `/fso-center-v2`, конечного `/` и кавычек. Для аккаунта другого владельца используйте его origin в нижнем регистре. Не вводите полный адрес репозитория.

Случайный FSO_CODE_PEPPER можно получить в SQL Editor нового проекта:

```sql
select gen_random_uuid()::text || gen_random_uuid()::text as fso_code_pepper;
```

Скопируйте результат в секрет один раз и сохраните приватно. После создания кодов экзаменов не меняйте его без необходимости: от него зависят сохранённые хеши кодов. Результат запроса не нужно загружать в GitHub.

SUPABASE_URL и SUPABASE_SERVICE_ROLE_KEY доступны размещённой функции как серверные переменные проекта. Не переносите service_role на сайт или в публичные файлы.

## 7. Настройте GitHub Actions

Создайте **Access Token аккаунта Supabase**: настройки аккаунта Supabase → Access Tokens → Generate new token. Токен должен иметь доступ к новому проекту. Это не пароль базы, не пароль администратора, не publishable key и не service_role key.

В **новом репозитории** GitHub: Settings → Secrets and variables → Actions.

На вкладке **Secrets** создайте repository secret:

| Name | Secret |
|---|---|
| SUPABASE_ACCESS_TOKEN | Токен аккаунта Supabase |

На вкладке **Variables** создайте две repository variables:

| Name | Value |
|---|---|
| SUPABASE_PROJECT_REF | Ref нового проекта: ровно его 20 символов |
| SUPABASE_PUBLISHABLE_KEY | Publishable key нового проекта либо legacy anon key |

Имена переменных копируйте точно, без пробелов. Публичный ключ допускается в Variables: он используется браузером. Секретный access token храните только в Secrets. Логин/пароль администратора и пять FSO_* сюда копировать не нужно: они настроены в Supabase.

## 8. Загрузите все файлы в GitHub

1. Вернитесь на Code нового репозитория, в ветку main.
2. Add file → Upload files.
3. Перетащите папки `site`, `supabase`, `scripts`, `tests`, а также `package.json`, `server.mjs`, `README.md`, `SETUP.md`, `.gitignore` и `SHA256SUMS.txt` из архива. Загрузка существующего README заменит стартовый README нового репозитория — это ожидается.
4. Проверьте пути перед сохранением: `site/index.html`, `supabase/functions/fso-api/index.ts`, `supabase/functions/_shared/domain.mjs`, `supabase/setup.sql`. Не `fso-center-new/site/index.html` и не `site/site/index.html`.
5. Commit changes в main. Если GitHub предлагает новую ветку, после загрузки создайте Pull Request и выполните Merge в main.
6. Проверьте наличие `.github/workflows/publish.yml`. Папки с точкой иногда пропускают при перетаскивании. Если файла нет: Add file → Create new file → имя `.github/workflows/publish.yml` → вставьте весь текст этого файла из архива → Commit changes в main.
7. В новом репозитории должен быть **только один** workflow публикации из этого комплекта. Не добавляйте прежние pages.yml, deploy-api.yml или recover-api.yml.

`site/config.js` в исходниках имеет mode: local — это штатная заготовка для локального запуска. При публикации workflow сам заменит его на конфигурацию нового Supabase из Variables. Вручную вставлять ключ или переключать режим в файле не нужно.

## 9. Выполните единый запуск публикации

1. Если ещё не сделали: Settings → Pages → Source → GitHub Actions.
2. Actions → **Publish FSO Center**. После загрузки workflow он может запуститься автоматически.
3. Если запуска нет или первый запуск был до заполнения настроек: Run workflow → main → Run workflow.
4. Дождитесь успеха всех этапов:

| Шаг | Что проверяется / выполняется |
|---|---|
| Test complete project | 36 тестов приложения и развёртывания |
| Generate public website config | Ref и публичный ключ корректного типа; создание config.js для Pages |
| Deploy matching Supabase function | Публикация fso-api в новый проект без Docker |
| Verify live API version and capabilities | Версия 2026-10-17-new.1, четыре типа вопросов, действия с результатами и рабочий каталог |
| Publish website | Публикация site/ на GitHub Pages |

Сайт публикуется после успешной проверки API, поэтому отдельный ручной Deploy FSO API не нужен. Если любой шаг падает, откройте именно его лог. Перезапуск «зелёного» старого коммита вместо актуального main не исправит новые файлы.

Выпуск не публикует миграции автоматически: создание схемы уже выполнено в шаге 4. Код функции не содержит пароли или ключи вашей учётной записи.

## 10. Откройте сайт и активируйте первый экзамен

1. Адрес возьмите из Settings → Pages или из последнего шага Actions. В примере: `https://winderingen.github.io/fso-center-v2/`.
2. Откройте адрес в новой вкладке, при необходимости Ctrl+F5. Поле config.js на опубликованном сайте уже должно иметь mode: supabase; оно генерируется Actions.
3. Откройте «Кабинет администратора», введите FSO_ADMIN_LOGIN и пароль пользователя, созданного в Supabase Authentication.
4. В «Банк вопросов» уже есть учебные вопросы всех четырёх типов. Создавайте свои категории и заменяйте примеры.
5. «Тесты и экзамены» → «Пробный вступительный экзамен» → «Изменить». Укажите категории/вопросы, доступные отделы, время и проходной балл.
6. Нажмите «Сгенерировать» для кодового слова, затем отметьте публикацию и **сохраните** экзамен. Генерация без сохранения не активирует новый код.
7. Для пробной сдачи выберите нужный отдел, введите звание, ФИО персонажа, удостоверение `123-456` и сохранённый код. ФИО инструктора и его жетон можно оставить пустыми. Если жетон указан, он тоже должен соответствовать `123-456`.
8. По завершении курсант видит только процент. Администратор видит ответы, ошибки и данные инструктора в «Подробнее» и CSV.
9. Для тестовой попытки в «В процессе» доступны «Завершить» и «Завершить и удалить». Для готового результата — «Удалить». Все эти действия требуют подтверждения; удалённая попытка исключается из статистики.

Не проверяйте на данных реального сотрудника, если хотите просто испытать удаление: создайте отдельную пробную попытку. После закрытия вкладки результат не гарантированно завершается немедленно — для зависшей попытки предусмотрено принудительное завершение администратором. Завершение по таймеру обрабатывается сервером при последующем обращении к API.

## 11. Как обновлять сайт дальше

Меняйте исходники в **этом новом репозитории** и сохраняйте в main. Один Publish FSO Center обновит функцию и интерфейс в одном процессе. Данные таблицы при этом сохраняются. Не меняйте project ref, origin или pepper при обычном обновлении и не выполняйте setup.sql для «перезапуска сайта».

Старый сайт и старый Supabase можно оставить как независимую резервную систему на время проверки. Этот комплект их не меняет и не переносит из них сотрудников, результаты или кодексы.

## 12. Если запуск остановился

| Ошибка / симптом | Что сделать |
|---|---|
| Publish FSO Center не появился | Создать .github/workflows/publish.yml именно на main |
| Ref должен содержать 20 символов | Variables → SUPABASE_PROJECT_REF: ввести ref, не полный URL и не имя проекта |
| Не задан publishable key или запрещён service_role | Взять Publishable/anon key из нового Supabase и сохранить в SUPABASE_PUBLISHABLE_KEY |
| CLI Unauthorized / Forbidden | Проверить Secret SUPABASE_ACCESS_TOKEN, срок токена и права владельца на новый проект |
| API HTTP 500 | Проверить выполнение setup.sql, пять FSO_* секретов и логи fso-api в новом Supabase |
| Missing FSO_ADMIN_* / FSO_CODE_PEPPER | Создать недостающий секрет в Edge Functions → Secrets; затем Run workflow на main |
| «Недопустимый источник запроса» | FSO_SITE_ORIGIN должен быть только https://ИМЯ.github.io, без пути репозитория и конечного слеша |
| Invalid JWT / Missing authorization header на открытом каталоге | Проверить успешный шаг Deploy matching Supabase function. Он должен публиковать fso-api с --no-verify-jwt |
| API version mismatch | Ref и ключ должны принадлежать новому проекту; дождаться успешного развёртывания функции из этого комплекта |
| На сайте «Версии сайта и API не совпадают» | Run workflow → main и дождаться всех шагов, затем Ctrl+F5; не смешивать файлы старых пакетов |
| Неверное имя/пароль администратора | Использовать FSO_ADMIN_LOGIN и пароль нового Auth-пользователя; сверить UID, email и подтверждение email |
| Таблицы загружаются, но не сохраняется «Порядок действий» | Проверить, что API-проверка прошла в том же проекте, на который указывает опубликованный config.js |
| На Pages выводится README | Source должен быть GitHub Actions; workflow публикует site, не корень репозитория |
| В списке нет экзамена | По умолчанию он черновик. Сгенерировать и сохранить код, включить публикацию, проверить выбранный отдел |

Если нужна дополнительная диагностика, передайте название упавшего шага и его текст ошибки. Не отправляйте значения Secret, пароли, Authorization headers или экспорт всей базы.

## 13. Резервная копия данных

Для периодического сохранения материалов и результатов используйте в SQL Editor нового проекта:

```sql
select id, version, data from public.fso_state where id=1;
```

Скачайте CSV и храните приватно. В data могут быть персональные данные игровых персонажей, коды экзаменов и служебные поля попыток; копия не предназначена для публичного репозитория. Исходники сохраняются историей GitHub, а учётные записи Authentication и секреты функции настраиваются отдельно от fso_state.

Официальные справки: [GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site), [публикация Supabase Functions](https://supabase.com/docs/guides/functions/deploy), [настройки Supabase Auth](https://supabase.com/docs/guides/auth/general-configuration).
